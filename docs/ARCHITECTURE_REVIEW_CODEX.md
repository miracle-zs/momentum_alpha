# 对架构评审的复核意见

> 复核对象：[`ARCHITECTURE_REVIEW.md`](ARCHITECTURE_REVIEW.md)  
> 复核日期：2026-09-04  
> 复核结论：报告大约七成判断成立，但将已证实的问题、架构选择和推测性风险混在了一起。

## 总体结论

Gemini 的报告适合作为问题清单，但不宜直接作为重构方案执行。当前项目并不是“架构失控”，而是已经形成了一个有明确边界的模块化单体，同时存在几个需要优先处理的交易执行、调度和可观测性问题。

我实际运行了当前测试套件：678 个测试全部通过。这个结果能够证明测试当前通过，但不能证明代码拥有 100% 覆盖率；项目中没有看到足以支持该结论的覆盖率报告或配置。

## 逐项核对

| 评审观点 | 判断 | 复核意见 |
|---|---|---|
| 策略核心是纯函数、无 I/O | 基本正确，但表述略满 | `evaluate_minute_close` 的边界清晰，不直接访问网络或数据库；不过 frozen dataclass 内部仍包含可变的 list/dict，因此不能严格称为完全不可变。见 [`strategy.py`](../src/momentum_alpha/strategy.py) 和 [`models.py`](../src/momentum_alpha/models.py)。 |
| 市价入场 + 固定止损预算存在真实风险 | 正确，且优先级高 | [`sizing.py`](../src/momentum_alpha/sizing.py) 主要按入场价与止损价计算数量，没有将滑点、手续费、资金费、跳空和可用保证金纳入。因此它是模型风险预算，不是实际损失上限。 |
| 下单具备幂等性 | 大体正确 | Broker 会使用 client order ID 查询已有订单，并对暂态错误进行查询/重试。这个设计值得保留。见 [`broker.py`](../src/momentum_alpha/broker.py)。 |
| 新止损替换采用先新后旧 | 正确 | 已有止损的替换流程是先提交新止损、再取消旧止损，降低了保护空窗。 |
| 可以杜绝无止损裸仓 | 过度表述 | 新仓仍然是先提交入场、再提交止损。若入场成功而止损提交及后续修复均失败，仍可能出现裸仓；当前代码是“预检查 + 修复 + 验证”，不是绝对保证。见 [`poll_worker_core_live.py`](../src/momentum_alpha/poll_worker_core_live.py)。 |
| SQLite/WAL 会导致高频锁库 | 方向正确，结论过强 | 项目已有统一连接层、WAL、busy timeout、`BEGIN IMMEDIATE` 重试和原子状态合并。不过 SQLite 这里是数据库级写者串行，不是行锁；是否已经成为生产瓶颈，需要实际锁等待、写事务耗时和 `database is locked` 次数来证明。参考 [SQLite transaction 文档](https://sqlite.org/lang_transaction.html)。 |
| 应立即改成单进程 | 这是可选方案，不是必然结论 | 单进程可以减少 poll/user-stream 的状态合并复杂度，但也会扩大共同故障域。当前双进程 + SQLite 是项目明确选择的模块化单体方案，建议先测量再迁移。 |
| Shadow replay 已严格模拟真实组合约束 | 部分正确 | 连续策略/portfolio 模式处理了重叠和每日限制；但默认独立候选回放是分析模式，不能直接当作组合收益。见 [`skipped_base_replay.py`](../src/momentum_alpha/skipped_base_replay.py)。 |
| 149 个 Python 文件说明模块碎片化 | 证据不足 | 项目中有不少有意拆出的 focused module 和兼容 facade，架构计划也明确要求保留这些边界。文件数量本身不是架构缺陷；更值得关注的是少数大模块和它们的真实耦合。 |
| scheduler 存在漏 tick | 正确，属于明确 bug | 当前只在 `second <= 2` 时运行；如果进程在第 3 秒之后才检查，该分钟可能永久跳过。见 [`scheduler.py`](../src/momentum_alpha/scheduler.py)。不过报告给出的修复示例若直接使用 `datetime.now()`，会破坏现有的时钟注入和测试模型。 |
| 使用 IOC 或 Price Protect 限制入场滑点 | 需要修正 | IOC 限价入场是可行方向，但必须处理部分成交和实际成交数量。Binance 的 `priceProtect` 主要用于条件止损/止盈触发保护，不是市价入场滑点保护。参考 [Binance Futures New Order 文档](https://developers.binance.com/docs/derivatives/usds-margined-futures/trade/rest-api/New-Order)。 |

## 最值得优先处理的问题

### 1. 新仓入场后的止损保护

当前 replacement stop 流程相对稳健，但新仓流程仍存在不可消除的顺序窗口。建议补强：

- 明确记录入场成功、止损失败、止损修复失败三种状态；
- 使用实际成交数量创建止损，覆盖部分成交场景；
- 修复失败后设置清晰的保护策略，例如暂停后续入场、告警，必要时执行受控的风险退出；
- 将 Binance 的保证金不足、数量上限、名义价值限制等错误按错误码分类，而不是只记录通用提交失败。

### 2. scheduler 的漏 tick

需要先定义语义：错过一个分钟点后，是补跑最近一个已收盘分钟，还是补跑所有错过的分钟。对于当前实时策略，通常应选择明确的“最近已收盘分钟”策略，而不是无条件补跑所有历史分钟。

实现上应继续使用注入的 `now_provider`，并记录 tick 延迟和漏 tick 次数。至少应增加以下回归测试：第 3 秒启动、第 20 秒启动、handler 长时间运行，以及 handler 异常后恢复。

### 3. SQLite 连接策略和锁观测

不建议仅凭文件数量或 WAL 的存在就迁移数据库。更实际的短期工作是：

- 统一剩余裸 `sqlite3.connect` 的 timeout、busy timeout 和只读策略；
- 记录锁等待时长、写事务时长和 `database is locked` 次数；
- 保持计算过程在事务外，只在最终写入阶段持有写事务；
- 明确 analytics rebuild 与实时写入的调度关系。

如果观测结果显示锁竞争确实影响实时交易，再比较单进程、写入队列或其他持久化方案的收益和故障代价。

### 4. 入场滑点控制

不要把 IOC 和 `priceProtect` 当成同一个能力。可选路径是：

- 先利用已有成交和分析数据测量预期价与实际成交均价的滑点；
- 若滑点可预测，再考虑带价格上限的 IOC 限价单；
- 如果暂时保留 MARKET，则在订单簿冲击、价差或价格陈旧时降低数量或跳过入场；
- 设计限价单时必须处理未成交、部分成交、数量重新计算和止损数量同步。

## 对重构方向的建议

当前更适合继续深化已有模块边界，而不是按目录批量搬迁文件。优先寻找“深模块”边界：用较小的接口封装更多实现细节，并让执行、持久化、交易所适配器之间的依赖方向更明确。

特别是：

- 保留策略核心与 I/O 的现有 seam；
- 将交易执行失败分类、成交同步和保护状态做成清晰接口；
- 将 SQLite 连接策略统一成基础设施接口；
- 只有在测试覆盖、锁指标和运行时故障数据支持时，才考虑单进程或更换持久化方式。

## 最终评价

报告抓到的三个真实重点是：

1. scheduler 的窄时间窗口会漏 tick；
2. 市价入场和固定止损预算不能保证实际损失上限；
3. 双进程共享 SQLite 的写入与状态合并需要持续观测。

但以下结论需要降级或纠正：

- 678 个测试通过不等于 100% 覆盖率；
- SQLite WAL 不等于行级锁，也不等于必然高频锁库；
- 149 个文件不等于模块化失败；
- 默认 shadow replay 并非组合收益模拟；
- `priceProtect` 不是市价入场滑点保护；
- 当前止损流程降低了裸仓风险，但不能宣称绝对杜绝。
